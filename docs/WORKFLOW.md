# How a book is made

Each step below is a button in the app. Steps run in the background as a *run*; the Run panel shows every task, what it waits for and what it cost.

## 1. Sources

Add notes, textbooks, exercise collections and past exams, and mark each as Theory, Exercises, Exams or Mixed. **Prepare** then:

- splits every file into pages and marks pages whose text layer is garbled or empty (math in LaTeX-made PDFs, handwriting, scans);
- keeps each source's own table of contents, or reconstructs one from the page headings and labels it *inferred*;
- splits exam files into sessions and exercises and skips duplicate copies of a session. A session starts at "Esame di <course>", "Prova scritta", "Appello", "Compito" or "Tema d'esame" with a date (12/02/2024, 12 febbraio 2024 or 2024-02-12, on the line or in the header table after it). An exercise starts at "Esercizio", "Problema", "Quesito", "Domanda" or "Parte" with a number or letter, and sub-questions a), b), c) stay inside it. A paper written in Markdown is read like the same paper as a PDF: heading marks and bold or italic marks around a heading are ignored (`**Problema 1** (12 punti)`, `## Esercizio 2`), a pipe table gives one line per cell, so a date in the header table counts, and the same plain lines go to Split with AI. A solution section is headed "Soluzione", "Soluzioni", "Svolgimento" or "Risoluzione", alone or with a qualifier in brackets or naming the session ("Soluzioni (Appello del 12 febbraio 2024)"). A qualifier with a date sends the solutions to the session of that date, so solutions printed after all the papers still reach their own;
- uploads the sources to the book's NotebookLM notebook (once per file version);
- builds the topic map, assigns every exam question to its topics and counts the distinct exam sessions per topic. Items of exercise collections are not assigned to topics here, because they only serve as examples for the exercise writer, which finds them when it writes a chapter's exercises.

If the split of an exam file looks wrong, the Sources list says so and so does the Prepare run, which then shows a warning next to its completed status. The file gets a warning when no exercise was found, when the whole file came out as one session because no session heading was recognised, or when every session has at most one question. The list shows the sessions and questions found for each exam file. A file with a warning also shows two buttons in its row: Split with AI (described next) and Mark as not an exam, which changes the role to Theory, the one role whose questions no longer count for exam frequency or practice, and can be undone from the same row. The Run panel lists the warnings of a finished run and calls it Completed with warnings. A book prepared before the split was recorded gets the same counts and warning on its next Prepare run, worked out from the stored questions, which stay as they are.

**Split with AI** is the way out when the text rules do not know a paper's layout. You ask for it on one exam file, and it never runs by itself. The bulk model gets the first lines of each page (as plain text, with Markdown marks removed), then the lines that look like headings (at most 25 lines per page), and answers with the sessions and exercises, each with the page and the exact line where it starts, and where each exercise's official solution starts when the paper prints one. A session is named as the text rules name it ("Appello del 12 febbraio 2024"), so the same paper split either way is stored once. The builder accepts the answer only when every quoted line is on the page the model names, the boundaries are in page order and every exercise lies inside its session, every solution lies in the session of its exercise and no two exercises share a solution. Then it stores the sessions and questions the same way the text rules do and the topic map classifies them. An answer that does not hold up changes nothing, and the warning stays. A file whose questions you edited or checked already is not split again, because that would replace them. The check is made again right before the replacement, so an edit made while the model was working is kept. The action is refused while a Prepare run of the book is active, because the topic map of that run would not wait for the new questions. If a source is not an exam, change its role in the Sources list.

**Deleting a source** removes the pages, the stored file and the questions read from it, together with the review problems about those questions, so nothing from it keeps counting or stays in the book. Two kinds of question stay: one you edited and one a chapter already uses. They lose their source and page range and are your own from then on, and the delete says how many went and how many stayed. A source you only exclude keeps its questions but they stop counting, and a paper that another file repeats is stored again as a new copy: only questions that count are compared when a session is checked for being a duplicate. So the corrected upload of an exam file, after deleting the first one, is stored in full.

## 2. Course program

Once the book exists, open **Book setup**, paste the program from the PoliTo course guide or give the guide's address, then press **Read program**. The planning model turns it into a list of items, each with its title, the program's own wording and whether the exam asks its proof, plus the exam format (written, oral, which proofs). Include the "Modalità d'esame" part when the guide has it, because it decides how much weight proofs get. You can edit every item, and reading the program again keeps the key of every item whose title stays the same, so the outline's references to it still work. An item whose title changes gets a new key.

Under *What goes in the book*, *Sections outside the course program* sets what happens to material the program doesn't ask for when you align the book (step 6): **Remove off-program sections** (the default) or **Keep them with a note**.

A book without a program works as before: it covers the topics of its sources, and the exams decide how deep each one goes.

## 3. Outline

**Generate outline** asks the planning model for a common index: chapters, sections, objectives, depth and the topics each section covers. With a program, every item goes in the section or sections that teach it or is listed as left out with a reason, and source topics outside the program are excluded with a reason. A topic the program or the exams need as a prerequisite can stay as a short recap inside a related section, without a section of its own. The exams then decide only the depth: topics in many sessions get *deep* sections and more exercises. Without a program, topics in no session keep a section and the baseline exercises unless you exclude them with a reason. Edit anything, then **Approve outline**. Drafting always uses the approved version.

## 4. Drafting

**Generate book** works chapter by chapter. Chapters run side by side, but the sections of one chapter are written in order, so the writer of section 2 reads the summary and the formula keys of section 1. Evidence is gathered for all sections of a chapter at once. If a section fails, the sections after it in its chapter wait, the other chapters go on, and the run ends as failed with the cause shown on the section that failed. A retry of that section lets the rest of its chapter continue.

1. *Evidence*: NotebookLM (or the local reader) answers a question about the section by quoting the sources. Each quote is located on its page; unlocated quotes are dropped. The most cited garbled pages are transcribed by a vision model so the writer sees clean formulas. The writer gets the verified quotes, the evidence reader's answer and the full clean text of at most two of those transcribed pages, the most cited first. A page with a good text layer is not sent whole, because the quotes come from it.
2. *Writing*: the writer gets the section's objectives, its program items and the exam format, the chapter plan, summaries of earlier sections, known formula keys, the notation, the subscripted symbols that the exam papers use on the section's topics (`f_c`, `v_{out}`, taken from the statements of the questions that count, with the instruction to use them for the same quantities unless they conflict with the book's notation, so the book and its practice agree) and the evidence, and returns the section with citation markers and the specs of any figures it adds. The section is the plain-text body of the answer, and only the small fields (the figures and the summary) follow it as JSON after a line `<<<META>>>`, so no formula is ever inside a JSON string. A worked example and a typical-mistake box are asked only when the section teaches a method or a computation, and the writer is told never to add sentences to reach a length and never to mention its sources to the reader ("the notes", "the material provided", what they do or do not contain). The model-commentary lint flags such a sentence as a blocker in Italian and English. A gap in what the sources cover is the alignment check's job, never a sentence in the book. The word range of each depth (400-800, 800-1,500, 1,200-2,200) is unchanged and only describes the usual size. The repair of a formatting problem and the lab example's code are answered the same way. The writer is offered only the figure kinds of the book's subject area (a mathematics book gets plots, a chemistry book also gets structures and diagrams), and by default only adds a figure where the student has to see something to follow the text. Before a figure is built, a cheap model drops the decorative ones; the same check runs on the figures a fix adds. Proofs follow the exam format. A recap section that teaches no program item gives proofs only as far as the explanation needs and never marks them. In the other sections, when the exam asks for proofs, every theorem with a standard proof gets it in full after the line "**Dimostrazione richiesta all'esame.**" ("**Proof asked at the exam.**" in an English book), and when the program lists only some proofs, only those results get it. A written exam without proofs keeps them brief and unmarked. Plots, structures and the chemistry diagrams are drawn by the builder from validated specs, so curves match their formulas. A plot can have a logarithmic x or y axis (`xScale`, `yScale`: `linear` or `log`), which needs a positive range and is sampled in the exponent. A Bode plot is asked for as two plot figures, magnitude and phase, with the same log frequency axis, one after the other. Any other figure is a "drawing": the writer describes it in English (`shows`) and a separate illustrator model writes the drawing code, which the builder compiles, repairs when it fails, and checks once by showing the model its own picture. A drawing that does not compile after two repairs is dropped with a note, as any failed figure is. To change a drawn figure in a fix, the writer returns a new `shows`, which draws a new figure.
   After the answer parses, the writer checks its own section once: it gets one more message in the same conversation, which asks it to look at every statement for missing hypotheses, every derivation step, every computation and numeric result with its unit and sign, and every reference to a formula key. It answers `OK` or the full corrected answer in the same format. A correction replaces the draft only when it parses, keeps every heading, formula key, `:::` block, image, figure and citation marker of the first draft (a paragraph rewritten whole may lose its marker), and does not open or close with a note about what it changed (the follow-up forbids one, and a real run produced one anyway). If the follow-up fails (a usage limit, a timeout) or the correction does not hold up, the first draft stays and nothing else changes. The draft task records which happened as `selfCheck`: `ok`, `corrected`, `kept` or `skipped`, and `selfCheckNote` says why a correction was not used. Exam guides do not get this turn. It costs one more call per section, mostly output tokens, because the writer's context is already loaded. It is the book option `selfCheck`, on by default and without a screen yet: switch it off with `PATCH /api/projects/<id>` and `{"options": {"selfCheck": false}}`.
3. *Clean-up, lint and repair*: some fixes need no model. Function names KaTeX lacks, such as `\cotan` or `\sen`, become `\operatorname{...}`. A formula block reusing a key another section already defines keeps its math and loses the key. A link to a section id the model miscopied points at the section that id was meant for when only one matches, and becomes plain text otherwise. Terminal codes and control characters left in model output are removed, and a line break in the writer's text stays a line break. Display math is moved out of sentences, and statements are numbered per chapter at compile. A reference to a formula reads "(7.2)" in the reader: a chip in the same chapter, a link to the formula in another chapter, and parentheses the writer put around it are dropped so it never shows as "((7.2))". Formatting problems that break the reader then trigger one repair request; what remains becomes an issue. A placeholder such as `[?]` or `???` is a blocker, and so is a literal backslash followed by `n` or `t` in text outside math and code, which is a line break or a tab that was never decoded. The lint covers every book text, questions and solutions included, so Validate and the export stop on it whatever path wrote the text.
4. *Exam guide*: every chapter whose topics appear in past exams closes with an exam guide, "Come viene chiesto all'esame" in an Italian book and "How the exam asks it" in an English one, written from its classified exam questions. The builder computes the session counts in it ("N of M sessions"), not the model.
5. *Introduction*, *practice* (authentic exam questions re-read from page images, generated exercises up to the topic targets, labeled exam-style practice when a chapter has no real exam questions; question text that would not render gets the same single repair, and exam questions have no hints, as on the day), *extras* (graphs and Python or MATLAB examples where they help, all checked) and an *independent review*. A graph or example whose check failed is left out of the export and listed as a finding on the Export screen. A graph can have a log axis too, shipped as a Plotly axis of type `log`, and a Bode plot is one graph with a second graph (`pair`) on the same frequency axis, stored as two graphs of the section; the numeric check reads a log axis in data units and counts only positive values on it. An edited graph is checked again when you save it in Extras, and an edited example goes back to draft because running it needs the sandbox.

   - *Reading exam questions*: when a session has two or more questions still to read, one call reads them all from the same pages instead of one call per question, so the pages are sent once. The answer is plain text, one part per question (`@@@ statement 2`, `@@@ solution 2`, or `@@@ unreadable 2`), so no statement or solution is a JSON string and a line break arrives as a line break. It must list exactly the numbers of the stored questions, none missing and none invented, and a malformed answer gets one repair turn. If it still does not hold up, or if the session spans more than 12 pages or more than 60,000 characters of transcript, each question is read by its own call as before. A question read on its own gets the same plain-text answer. A question you edited, or one already read from the pages, is not read again.
   - *Examples from exercise collections*: the exercise writer gets at most 6 items of the collections as examples of level and style. Items already assigned to the chapter's topics come first. The others are found by searching the collections' pages for the words of the chapter's topic and section names, then keeping the items whose own text contains those words, those with a known answer first. This costs no model call.
   - *Checking solutions*: a second model solves each exercise again and compares. When the final answer is one or more numbers with a unit, that same answer also carries a short Python computation of the values from the statement. It runs in the same sandbox as the Python examples and its values are compared with the ones the solution states, within the number of significant figures the solution gives (4.7 kΩ and 4700 Ω are the same value). A value that differs is a blocker that names both numbers, and the reviewer model is asked, as for any different result. A computation that fails, prints nothing or cannot be paired with a stated value is ignored, and so is any answer that is not a number, such as an expression or an interval.

With the first-chapter gate on (the default), the run stops after chapter 1. Read it, fix what you need, then press **Continue** in the Run panel; the remaining chapters use the same prompts you have now seen working.

## 5. Review

The Review tab lists lint findings, failed checks and reviewer issues, each pointing at the exact text. For each one: edit the text yourself, **Fix selected issues**, or **Accept as is**.

**Fix** applies the fix to the text. Earlier versions stay in the section's history, so you can restore any of them. Before a fix is applied it passes these checks:

- a change that would delete a heading, a formula or another special block, drop a formula key, leave a `:::` fence open, or break a formula is left out, and its issue stays open with the reason;
- a change that raises the count of blocker or major lint findings for any one rule is reverted, even if it lowers others (a change that swaps one finding for another of the same rule and severity passes this guard);
- a cheap second model reads each change against the issue and drops any that adds an error or removes more than asked;
- a fix that would remove more than a fifth of the text is not applied; it waits as a proposal in the Manuscript, and so does a fix for a section you edited while it ran.

The fix model is told these rules in its prompt, generated from the guard's own limits, so it does not delete a heading, a formula or more blocks than the guard allows. It reads only the evidence notes that the blocks it fixes cite, and the whole packet when it cannot tell which blocks those are. It answers in plain text, one part per changed block, so LaTeX backslashes arrive as written and are not eaten by a JSON string. A malformed answer gets one repair turn.

A fix model can also answer that the section already resolves an issue, which happens when an earlier fix or an edit by hand dealt with it. The cheap model then checks that claim against the current text. A confirmed issue is closed as fixed with the reason "Already resolved in the current text", an unconfirmed one stays open with the reason shown, and so does one whose section changed while the fix and the check ran.

Two kinds of issue the text fix cannot solve go elsewhere. A figure issue that asks for a figure where none exists goes to the figures pass for that section, with the issue as the brief, and each figure it proposes names the issue it answers, so an issue closes only when a surviving figure answers it. A graph that failed its check is redrawn, one redraw for each failing graph (a Bode pair has two), and each redraw answers only the issues about its graph. The graph of the answer with the failing graph's id replaces it (the only graph of the answer when none has the id), and only when it passes and the author did not edit or delete that graph meanwhile. In both cases the issue stays open with the reason when nothing lands. A figure issue about a figure that is already in the section stays with the text fix.

An instruction you give in the Manuscript ("regenerate with instruction") always becomes a proposal. Proposals never replace your text until you accept them.

**Run review** reads the whole chapter only the first time, and that review reports everything. A minor issue there means a wrong word, symbol, unit or reference that could mislead a student. Style, wording and "could be clearer" are not reported at any severity. After the first review it reviews only the paragraphs, formulas and boxes written since the last review, such as the text a fix changed. It receives the sections that changed in full, the other sections as the short summaries their drafts recorded, and the evidence of the changed sections only, which made the prompt a third of the first review's size on a test chapter where one section of four changed. It reports only blockers and majors, and any minor it still returns is dropped before the second opinion. Findings outside the new text are dropped too. Open issues on text that didn't change stay as they are. A chapter with no new text costs no model call. The reviewer also sees the issues you accepted or dismissed and the ones already fixed, and does not raise them again. Only blockers stop an approved export; majors and minors do not have to reach zero.

A review that leaves no open blocker or major says so. The result of each chapter review carries `clean` and `openSerious`, and the project summary the Review screen reads (`GET /api/projects/:id`) carries `review: { clean, openSerious, reviewedAt }`. `clean` is true when every chapter with text was reviewed at its current text and no blocker or major is open or waiting as a proposal anywhere in the book. Text changed after a review, a new open blocker or a new proposal makes it false again. Reviews and fixes still start only when you press the buttons: nothing loops by itself.

Before this, every review re-read the whole chapter and reported a different handful of old passages each time. On Fisica 1, about 80% of the issues in the second and third reviews were in text the earlier reviews had already read, so running a review never brought the count to zero.

**Every finding gets a second opinion** before it reaches the list: another model (the **Second opinion** role, Claude Sonnet by default) re-reads the passage with the sources. It drops findings that are not real, such as a counterexample the setting excludes, and can lower a severity but never raise it. Dropped findings stay visible under **dismissed**, with the reason, and the reviewer is told not to raise them again. If the second opinion can't run, the findings stay as the reviewer wrote them.

**Full review** reviews every section on its own call instead of the whole chapter at once, so fewer problems are missed. It reports everything, as the first review does. It costs about as much as 3 to 5 normal reviews; use it once, before the final export. It replaces the open review issues with what it finds.

Fixes for review issues make the smallest edit that corrects the sentence. The check that decides whether a fix is applied rejects one that adds more than one new sentence of claims or caveats, because those sentences were what the next review found fault with. When that check can't run, the other guards decide alone and the limit isn't enforced. Program issues (step 6) are the exception: a fix for a thin section or a missing proof may add the material it needs, and a fix for an off-program passage may delete whole subsections, formulas and boxes. When such a fix is applied directly, a formula it deletes becomes a plain name wherever other sections referred to it. Accepting the same fix as a proposal doesn't do this, so check those references yourself.

## 6. Alignment with the program

This step is for books that already exist, including ones written before they had a program. Add the program in Book setup first.

**Check alignment**, in the Review tab, sends one planning call with a digest of the book: headings, statement labels, whether each proof is present, lengths and exam sessions, but not the full text. The report has six groups:

| Group | What it lists | What **Align book** does |
| --- | --- | --- |
| Missing from the book | Program items no section teaches | If a written section is planned for the item, opens a review issue and the fix teaches it there. If the planned section isn't written yet, writes it. Otherwise adds a section where the check suggests and writes it |
| Too thin for the exam | Items taught more briefly than the exam needs | Opens a review issue, and the fix expands the section |
| Proofs the exam asks | Proofs the exam asks that the section doesn't give | Opens a review issue, and the fix adds the proof |
| Outside the program | Sections and passages the program doesn't list and no in-program part of the book needs | Removes a section, or keeps it with a note, as Book setup says. A passage becomes a review issue whose fix cuts it, or puts the note before it in keep mode |
| Order | A section placed before one it depends on | Nothing: move the section in the outline yourself |
| Exam guides | Chapters without an exam guide | Adds the guide and writes it from the exam questions |

Ids, keys and quotes in the report that don't match the book are dropped. A new report starts with every finding selected that Align book can apply. Deselect the ones you disagree with, then press **Align book**. A new section in a finished chapter gets its evidence, a draft and a chapter review, while the chapter's introduction, practice and graphs are not redone.

A section needed to understand the in-program parts counts as needed, even when it is outside the program. When a removed section was linked from other sections or they used its formulas, those links become their plain label and the formula references become the formula's name. Generated exercises that link to a removed section or use its formulas leave the book with it. A past exam question or a source exercise still in the book that does the same keeps the section, which is then kept with a note, and so is a chapter's only section.

Removing a section writes a new outline revision, rewrites the links and formula references in other sections and takes the generated exercises out of the book, as described above. The section's own text stays in the database, and the report lists every removed section with a **Put back** button that returns it to where it was. The links that became plain text and the detached exercises don't come back with it.

## 7. Export

**Validate** runs the reader's own validator plus the builder's lints on the compiled book. Each finding names the section or question it comes from and links to it. **Fix with AI** sends the errors and warnings to the same fix as **Fix selected issues**: sections get a guarded fix, and questions are rewritten and checked again. Findings in generated files, such as a chapter's exam page, go away when the question behind them is fixed. **Approve and export** is available when no blocker is left; **Export draft** always works and is named `-draft`. Every export is reopened and compared with what was compiled before it is offered for download.
